# 054 - CSRF, XSS, and injection protection

A browser application accepts data from users, stores it, sends it through APIs, and eventually renders it as a page. Security problems arise when the browser treats data as an instruction, a database interprets data as query syntax, or a server accepts a state-changing request that the user did not intend.

This chapter builds on the cookie-backed session from chapter 051 and the authorization checks from chapter 053. It covers cross-site request forgery (CSRF), cross-site scripting (XSS), and injection risks in a React, Express, and MongoDB application.

## Learning goals

After this chapter, you should be able to:

- Explain why cookie-authenticated APIs need CSRF protection.
- Protect state-changing requests with a session-bound CSRF token.
- Keep safe HTTP methods free of state changes.
- Render plain user content safely in React and recognize dangerous HTML sinks.
- Sanitize user-authored HTML only when rich HTML is an actual requirement.
- Build MongoDB filters from validated, expected scalar values.
- Identify related injection risks in SQL, shell commands, templates, and paths.

## Treat input as data

Validation, authorization, output encoding, sanitization, and parameterization solve different problems:

| Control | What it checks or changes | Example |
| --- | --- | --- |
| Validation | Whether input has an allowed shape and value | A status must be the string `draft` or `published`. |
| Authorization | Whether the caller may perform this action | A member may edit only their own draft. |
| Output encoding | How data is represented in a particular output context | React renders a title as text instead of parsing it as markup. |
| Sanitization | Removes unsafe markup when a feature intentionally accepts markup | A rich-text editor permits a small, reviewed set of HTML. |
| Parameterization / structured APIs | Keeps query or command syntax separate from data values | Build a MongoDB filter with fixed keys and validated scalar values. |

A value can be valid but still unauthorized. A value can be authorized but still unsafe to render as HTML. Do not use one control as a substitute for the others.

## Cross-site request forgery

### What CSRF attacks exploit

Browsers automatically attach cookies to requests that match the cookie's domain, path, security, and SameSite rules. If a person is signed in to an application, a malicious page may cause that person's browser to send a request to the application. The attacker's page usually cannot read the protected response, but it may still cause an action such as changing an email address or creating a transaction.

CSRF primarily affects credentials that a browser sends automatically, especially session cookies. A bearer token that application code explicitly adds to an authorization header is not automatically attached in the same way, but it can introduce other risks such as theft through XSS.

### Protect state-changing actions

Use `POST`, `PUT`, `PATCH`, or `DELETE` for state changes. `GET`, `HEAD`, and `OPTIONS` must not change application state. A crawler, preview, browser prefetch, or cross-site link can trigger a safe-method request without the user intending a mutation.

For a cookie-authenticated application, use a CSRF defense that fits the architecture:

- A **synchronizer token** is generated by the server, associated with the user's session, delivered to the legitimate application, and returned in a request header or form field. The server compares it with the session-bound value.
- A **signed double-submit token** can suit a stateless design when implemented with a cryptographic binding to the user's session. A plain token cookie copied into a request header is not a safe substitute.
- **Origin or Referer validation** can add defense in depth on state-changing endpoints when the expected origins are configured precisely.
- Cookie attributes such as **SameSite**, **Secure**, and **HttpOnly** reduce exposure, but do not by themselves cover every deployment and browser situation.

A synchronizer token should be unpredictable, session-bound, and unavailable to an unrelated site. Send it in a custom header or form field, not in a URL. Do not log it. When login regenerates the session, fetch a fresh token for the new session.

Chapter 051's `csrf-sync` example uses this pattern: the browser requests `GET /api/csrf-token`, receives a token, and sends it in the `x-csrf-token` header on state-changing requests.

### CORS is not a CSRF defense

Cross-Origin Resource Sharing (CORS) controls which browser origins may read certain cross-origin responses. It does not stop every cross-origin request from being sent. A form or other simple request may reach the server even when the attacker's page cannot read its response.

Use a strict CORS allowlist for cross-origin applications, and separately enforce CSRF defenses for cookie-authenticated state changes. Never treat a permissive CORS policy as authorization or as a substitute for a CSRF token.

### Cookie and token considerations

- Use HTTPS and the `Secure` cookie attribute in production.
- Keep session cookies `HttpOnly` so ordinary page scripts cannot read the session ID.
- Set an intentional `SameSite` value and understand whether the product needs cross-site cookies.
- Keep CSRF tokens separate from session IDs and authentication credentials.
- Do not store a synchronizer token in a URL or expose it to third-party scripts.
- Do not exempt a state-changing route simply because it is called by React.
- Ensure login and logout flows are covered according to the chosen token lifecycle.

## Cross-site scripting

### How XSS happens

Cross-site scripting occurs when untrusted data reaches a browser context where it is interpreted as code or markup. An attacker may then act with the privileges of the vulnerable site in the victim's browser.

Common forms include:

- **Stored XSS:** harmful content is saved, then shown to other users, such as a comment or profile field.
- **Reflected XSS:** request data is immediately included in a response without safe handling.
- **DOM-based XSS:** browser-side code takes an untrusted value and writes it to a dangerous DOM sink.

An API that returns JSON does not eliminate XSS. The React application may later render that JSON into a page.

### Render plain text through React

React escapes strings rendered as ordinary text. Use that default behavior for titles, comments, messages, and plain article content:

~~~jsx
function ArticleContent({ article }) {
  return (
    <article>
      <h2>{article.title}</h2>
      <p>{article.body}</p>
    </article>
  );
}
~~~

If the stored body contains a string such as `<img src=x onerror=alert(1)>`, React displays it as text rather than creating an image element with an event handler.

Avoid raw HTML sinks such as `dangerouslySetInnerHTML` for untrusted input. Also review direct DOM APIs such as `innerHTML`, string-based event handlers, `eval`, and dynamic script construction.

### When rich HTML is a product requirement

If users must author formatted HTML, ordinary text rendering will display the markup literally. Use a maintained HTML sanitizer with a narrowly defined allowlist, and only pass the sanitized result to the HTML sink. Keep the sanitizer updated and do not mutate the sanitized string afterward.

Sanitization and output encoding solve different cases. For plain text, render text. For rich HTML, sanitize according to the allowed HTML feature set. Never attempt to make arbitrary HTML safe by replacing a few angle brackets or filtering a few known tags.

URLs need their own policy. If a user can supply a link, validate its parsed scheme and any allowed destinations. HTML escaping alone does not make a dangerous URL scheme safe.

### Content Security Policy

A Content Security Policy (CSP) can restrict which scripts and other resources the browser may load. It is a useful additional layer, but it does not repair unsafe rendering or replace correct data handling. Start with safe rendering and add CSP deliberately; the next chapter discusses security headers and API hardening.

## Injection

### MongoDB operator injection

MongoDB filters are structured objects. If an API expects a string but accepts an object from the caller, the object may contain query operators.

An unsafe pattern is to pass caller input directly into a filter:

~~~js
const user = await User.findOne({
  username: req.body.username,
});
~~~

A caller could send an object such as `{ "$ne": null }` where a username string was expected. Depending on the query and framework behavior, that changes the filter's meaning.

Validate the type, allowed fields, and value first. Construct a new filter with fixed keys:

~~~js
const username = req.body?.username;

if (typeof username !== "string" || username.length > 32) {
  return res.status(400).json({ error: "Invalid username." });
}

const user = await User.findOne({ username });
~~~

Do not accept a client-provided MongoDB filter, sort object, projection, aggregation stage, or raw query fragment. Do not put `req.body` or `req.query` directly into `find()`, `findOne()`, `updateOne()`, or an aggregation pipeline.

### Allowlist filter fields and values

For a list endpoint, check that each query parameter has the expected scalar type, validate it against an allowlist, and then build the filter yourself:

~~~js
const allowedStatuses = new Set(["draft", "published"]);
const requestedStatus = req.query.status;

const filter = {
  organizationId: req.user.organizationId,
};

if (requestedStatus !== undefined) {
  if (
    typeof requestedStatus !== "string" ||
    !allowedStatuses.has(requestedStatus)
  ) {
    return res.status(400).json({ error: "Invalid status." });
  }

  filter.status = requestedStatus;
}

const articles = await Article.find(filter).limit(50);
~~~

The `organizationId` comes from trusted authentication context, not the query string. The status value is a plain string, not a query object. Apply the chapter 053 authorization policy to the results as well.

For sorting, map known names to fixed sort objects, such as `createdAt` to `{ createdAt: -1 }`. Do not accept arbitrary field names and directions as a database sort expression. Bound page size and validate numeric values before using them.

### Mass assignment

Passing an entire request body into a database update can let a caller change fields they do not own:

~~~js
// Unsafe: the request may contain role, ownerId, organizationId, or status.
await Article.findByIdAndUpdate(articleId, req.body);
~~~

Build an update object from validated fields that the operation allows:

~~~js
const updates = {};

if (typeof req.body?.title === "string") {
  updates.title = req.body.title.trim();
}

if (typeof req.body?.body === "string") {
  updates.body = req.body.body;
}

if (Object.keys(updates).length === 0) {
  return res.status(400).json({ error: "No editable fields were provided." });
}

await Article.updateOne(
  {
    _id: articleId,
    organizationId: req.user.organizationId,
    ownerId: req.user.id,
    status: "draft",
  },
  { $set: updates },
  { runValidators: true }
);
~~~

This example still needs the route's full input validation and authorization handling. The key idea is that the server selects fields and query operators; the caller supplies only values.

### Other injection surfaces

The same separation principle applies beyond MongoDB:

- Use parameterized queries or prepared statements for SQL.
- Avoid building shell commands by concatenating input. Prefer a library API; if a process must be started, use a fixed executable, an allowlist of permitted operations, and an argument array rather than a shell command string.
- Keep template source fixed and pass user values as data. Do not compile user input as a template.
- Normalize and validate file names and paths; do not let a caller choose arbitrary filesystem paths.
- Validate data at every trust boundary, including requests from internal services and background jobs.

Validation should match the destination and product rules. A generic blacklist of suspicious characters is fragile and may reject harmless input while missing dangerous syntax.

## A layered request flow

A protected state-changing API request should pass through distinct controls:

1. Parse a bounded request body.
2. Validate the CSRF token when the browser authenticates with a cookie.
3. Authenticate the session.
4. Validate input shape and scalar types.
5. Authorize the identity for the action and resource.
6. Construct database filters and updates from fixed keys and validated values.
7. Encode output safely for the destination, especially when React renders it.
8. Return a minimal response and log safe operational metadata.

The order can vary for a particular API, but none of these checks should be silently skipped. A valid CSRF token does not authorize the user, and valid input does not make unsafe HTML safe.

## Review checklist

- Do state-changing routes reject requests without a valid CSRF token?
- Do `GET`, `HEAD`, and `OPTIONS` remain free of state changes?
- Are session cookies configured deliberately, and is SameSite treated as one layer?
- Does CORS have an explicit origin policy without being mistaken for CSRF protection?
- Does React render plain untrusted values as text?
- Are raw HTML sinks avoided or supplied only with sanitized, trusted HTML?
- Are user-provided URLs checked for allowed schemes and destinations?
- Are request fields validated by type, length, and allowed values?
- Are MongoDB filter keys and update operators created by the server?
- Are user-provided operators, raw filters, and arbitrary sort objects rejected?
- Are secrets, session cookies, CSRF tokens, and sensitive request bodies kept out of logs?

## Common mistakes

- Relying only on `SameSite` cookies or CORS for CSRF protection.
- Allowing a state-changing action on a GET route.
- Putting a CSRF token in a URL or reading it from the session cookie itself.
- Treating CSRF tokens as proof of identity or authorization.
- Assuming React makes `dangerouslySetInnerHTML` safe.
- Sanitizing only at input time and then changing the sanitized markup.
- Passing an object from `req.body` or `req.query` straight into a MongoDB filter.
- Trying to block injection with a short list of forbidden characters.
- Relying on CSP or a WAF to compensate for unsafe rendering and query construction.

## Summary

Cookie-authenticated state changes need an explicit CSRF defense, and safe HTTP methods must remain non-mutating. Render plain user content as text; sanitize only when the product deliberately accepts rich HTML. For MongoDB and other interpreters, validate the expected data shape and build commands, filters, and updates from server-controlled structure. Keep authentication, authorization, validation, output handling, and CSRF checks as separate layers.
