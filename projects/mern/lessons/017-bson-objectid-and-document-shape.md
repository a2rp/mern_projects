# 017 - BSON, ObjectId, and Document Shape

## Learning goals

By the end of this lesson, you should be able to:

- Explain what BSON is and how it differs from JSON.
- Recognize common BSON types in a MongoDB document.
- Explain the structure and purpose of an ObjectId.
- Distinguish an ObjectId from a string that looks like one.
- Describe how null, missing fields, dates, arrays, and numbers affect document shape.
- Choose clear and consistent field types for an application.

## BSON stores MongoDB documents

MongoDB stores documents using BSON, a binary serialization format for document data. BSON represents familiar structures such as objects, arrays, strings, booleans, and numbers. It also supports data types that plain JSON does not represent directly, such as ObjectId, Date, binary values, and distinct numeric types.

A tool may display a MongoDB document with JSON-like syntax:

~~~javascript
{
  name: "Asha",
  active: true,
  topics: ["MongoDB", "Node.js"]
}
~~~

That display is useful for people, but the stored data is BSON. The distinction matters because two values that look similar in a display may have different BSON types.

## Common BSON types

| BSON type | Typical use |
| --- | --- |
| String | Names, labels, email addresses, and other text |
| Boolean | True or false state |
| Int32 or Int64 | Integer values that need a defined integer width |
| Double | Floating-point numeric values |
| Decimal128 | Decimal values that need decimal precision |
| Date | A point in time represented as milliseconds from the Unix epoch |
| ObjectId | A compact identifier commonly used for _id |
| Document | A nested group of named fields |
| Array | An ordered list of values |
| Null | An explicit empty or unknown value |
| Binary | Bytes such as file or encoded data |

MongoDB supports additional BSON types. Learn the common types first and choose one that represents the meaning of the data.

### JSON is not the full BSON type system

JSON has strings, numbers, booleans, null, arrays, and objects. Standard JSON has no native ObjectId or Date value. JSON also does not distinguish a 32-bit integer, 64-bit integer, double, and Decimal128.

When data is converted between BSON and JSON, special representations may be used to preserve types. A plain JSON string containing a date or identifier is still a string unless the application or database driver converts it to the appropriate BSON type.

## ObjectId

ObjectId is a BSON type commonly used for the _id value of MongoDB documents. MongoDB clients generally generate an ObjectId when an inserted document does not supply _id.

A typical ObjectId is displayed as a 24-character hexadecimal string inside an ObjectId wrapper:

~~~javascript
ObjectId("507f1f77bcf86cd799439011")
~~~

The hexadecimal text is a display representation. The value is a 12-byte BSON ObjectId, not an ordinary string.

### ObjectId structure

An ObjectId consists of 12 bytes:

- 4 bytes representing a timestamp in seconds since the Unix epoch.
- 5 bytes of random data generated for a client process.
- 3 bytes for an incrementing counter.

This structure helps clients generate compact identifiers without asking the database to assign a sequential number first. ObjectIds are designed to be highly likely to be unique, while the unique _id index enforces uniqueness within a collection.

### ObjectIds are approximately ordered, not exact timestamps

The timestamp portion means ObjectIds are approximately ordered by creation time. They are not a perfect clock or a guaranteed strict ordering:

- The timestamp portion has one-second resolution.
- ObjectIds created in the same second are not guaranteed to be ordered by creation time.
- They are generated by clients, whose clocks can differ.

Use an explicit Date field such as createdAt when the application needs a clear creation timestamp. Do not rely on extracting the ObjectId timestamp as a precise event time.

### Create and inspect an ObjectId in mongosh

The MongoDB Shell can generate an ObjectId:

~~~javascript
const courseId = ObjectId();

courseId;
courseId.toString();
courseId.getTimestamp();
~~~

The ObjectId value can be used as a document _id. Its string representation is useful for display or for transporting an identifier through an API, but a string and an ObjectId remain different BSON types.

The Node.js MongoDB driver provides its own ObjectId class from the mongodb package. Its import syntax is covered with the driver in a later lesson.

## BSON types shape application data

### Numbers

The number 5 and the text "5" are different values:

~~~javascript
{
  quantity: 5,
  quantityLabel: "5"
}
~~~

Choose a number for calculations and comparisons. Choose a string for digits that are an identifier or label, such as a postal code that must preserve formatting.

BSON offers multiple numeric types. JavaScript has one ordinary Number type for most numeric values, so the MongoDB driver handles BSON number conversions according to its APIs and options. For very large integers or exact decimal amounts, choose and handle the appropriate BSON numeric type deliberately rather than assuming every number has identical precision.

### Dates

Use a BSON Date for an instant in time:

~~~javascript
{
  createdAt: new Date("2026-01-15T10:30:00.000Z")
}
~~~

A date-looking string is not the same type:

~~~javascript
{
  createdAt: "2026-01-15T10:30:00.000Z"
}
~~~

The first is a date value. The second is text. Pick one representation consistently so sorting, date comparisons, and application logic behave as intended.

A BSON Date represents milliseconds from the Unix epoch. It does not preserve a named time zone; store and exchange instants in a consistent convention, commonly UTC.

### Null versus a missing field

A missing field is not the same as a field whose value is null:

~~~javascript
{
  name: "Asha"
}
~~~

~~~javascript
{
  name: "Asha",
  phone: null
}
~~~

In the first document, phone is absent. In the second, phone exists and has a BSON Null value. Decide whether absence and an explicit unknown or empty value have different meanings in the application.

Do not store JavaScript undefined as a normal data modeling choice. Use an absent field, null, or a concrete value according to the application's meaning.

### Arrays

An array stores an ordered list of values:

~~~javascript
{
  tags: ["beginner", "mongodb", "backend"]
}
~~~

Elements in one array should usually follow a consistent type and meaning. A tags array containing strings in some records and nested objects in others is harder to validate and use.

## Choose a consistent document shape

A document shape is the set of fields, types, and nesting conventions an application expects for a kind of record.

For a course record, a consistent shape might use:

~~~javascript
{
  title: "MongoDB Basics",
  published: false,
  level: "beginner",
  createdAt: new Date("2026-01-15T10:30:00.000Z"),
  tags: ["database", "documents"]
}
~~~

Before storing data, decide:

- Which fields are required?
- Which fields are optional?
- What BSON type does each field use?
- Does a field contain a scalar value, an array, or a nested document?
- Does an absent field mean something different from null?
- Are values consistent across documents in the same collection?

MongoDB's flexible schema allows different documents to have different fields by default. It does not mean the application should use inconsistent types for the same field. A deliberate shape makes validation, querying, and future changes easier.

## Identifier types must match

Consider a document whose _id is an ObjectId:

~~~javascript
{
  _id: ObjectId("507f1f77bcf86cd799439011"),
  title: "MongoDB Basics"
}
~~~

The string "507f1f77bcf86cd799439011" contains the same hexadecimal characters, but it is not the same value as that ObjectId. A query comparing an ObjectId _id with a string value does not match merely because their display text looks alike.

When an API receives an identifier as text, validate it and convert it to the correct type before querying if the stored field is an ObjectId. Do not convert every string field into ObjectId; only convert values that are meant to be identifiers of that type.

An identifier is not authorization. Knowing a document's ObjectId should never, by itself, grant access to private data. The server must still verify that the current user is allowed to read or change the document.

## Common mistakes

### Treating an ObjectId as a string

Its display contains hexadecimal characters, but an ObjectId has its own BSON type. Convert an incoming string to an ObjectId only when the stored field uses that type.

### Treating the ObjectId timestamp as exact creation time

The timestamp portion has one-second resolution and ObjectIds are generated by clients. Store an explicit createdAt Date if the application needs a precise creation time.

### Storing dates as mixed types

If one document has a BSON Date and another stores an ISO date string for the same field, comparisons and application logic become inconsistent. Choose a representation and keep it consistent.

### Confusing null and a missing field

A missing field and an explicit null can mean different things. Decide which meaning the application needs and use it consistently.

### Using floating-point values for exact decimal amounts

Binary floating-point numbers cannot represent every decimal fraction exactly. For values such as financial amounts, choose a decimal-safe representation and use it consistently.

### Assuming flexible schema means flexible types everywhere

Documents can vary, but a field that is sometimes an array and sometimes a string complicates validation and application logic. Keep predictable fields consistent.

### Using an identifier as a permission check

An ObjectId identifies a record. It does not prove that a user is permitted to access the record. Perform authorization on the server.

## Key takeaways

- MongoDB stores documents as BSON, which supports more types than standard JSON.
- ObjectId is a BSON value, commonly used as _id, and is not an ordinary string.
- ObjectIds contain a timestamp, random component, and counter, and are only approximately ordered by creation time.
- Use explicit Date fields when the application needs creation or event timestamps.
- Keep number, date, null, missing-field, and array choices consistent.
- Convert API identifier strings to ObjectId only when the stored value uses that type.
- An identifier does not replace server-side authorization.
