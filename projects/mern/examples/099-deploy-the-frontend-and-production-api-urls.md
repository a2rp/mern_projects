# 099 - Deploy the frontend and production API URLs: Example

This example publishes one React frontend through an HTTPS edge and forwards the same-origin <code>/api</code> path to the Express service. It also records how the configuration changes if the API must use a separate origin.

Hostnames are illustrative. Keep all credentials in protected server configuration; every value in the frontend build or public runtime configuration can be read by visitors.

## 1. Choose the public request path

For this deployment, the browser uses one origin:

~~~~text
https://learn.example.test/          -> React entry document
https://learn.example.test/assets/*  -> hashed static assets
https://learn.example.test/api/*     -> Express API
~~~~

The frontend config uses the relative base <code>/api</code>. The edge routes that prefix to the API and routes other paths to the static frontend.

## 2. Set the public API base URL

For local development, a Vite server proxy can forward the API path to Express:

~~~~js
// client/vite.config.js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:4000",
        changeOrigin: true
      }
    }
  }
});
~~~~

The frontend can then use the same relative path in development and production:

~~~~text
# client/.env.example
VITE_API_BASE_URL=/api
~~~~

Resolve only known application paths:

~~~~js
// client/src/lib/api-url.js
const apiBaseUrl = (
  import.meta.env.VITE_API_BASE_URL || "/api"
).replace(/\/$/, "");

export function apiUrl(path) {
  const suffix = String(path).replace(/^\//, "");
  return apiBaseUrl + "/" + suffix;
}
~~~~

For query parameters, use <code>URLSearchParams</code> instead of concatenating raw user input. Keep the API prefix consistent across the frontend, edge route, and Express router.

## 3. Use the established session and CSRF helpers

This small request helper includes same-origin cookies and preserves existing request options:

~~~~js
// client/src/lib/api-fetch.js
import { apiUrl } from "./api-url.js";

export async function apiFetch(path, options = {}) {
  const headers = new Headers(options.headers);

  if (!headers.has("Accept")) {
    headers.set("Accept", "application/json");
  }

  return fetch(apiUrl(path), {
    ...options,
    credentials: "same-origin",
    headers
  });
}
~~~~

For state-changing requests, call the existing CSRF-aware request helper from the authentication chapters so it attaches the expected token header. Do not bypass that helper or change its token endpoint as part of deployment. If the frontend and API use separate origins, change the credential mode to <code>include</code> and configure exact-origin credentialed CORS on the API.

## 4. Keep environment files safe

The committed frontend template contains only public configuration:

~~~~text
# client/.env.example
VITE_API_BASE_URL=/api
~~~~

Ignore local environment files while retaining the example:

~~~~gitignore
# client/.gitignore
.env
.env.*
!.env.example
~~~~

A production frontend may use a different public API value, but no frontend variable contains <code>MONGODB_URI</code>, <code>SESSION_SECRET</code>, database credentials, or private cloud tokens. Keep those values in the API service's protected runtime configuration.

## 5. Optionally load public runtime configuration

If the same frontend artifact must be promoted between environments with different API URLs, publish a separate non-secret configuration file beside the app:

~~~~js
// public/app-config.js
window.__APP_CONFIG__ = Object.freeze({
  apiBaseUrl: "/api"
});
~~~~

Load it before the application bundle in the HTML entry:

~~~~html
<script src="/app-config.js"></script>
<script type="module" src="/src/main.jsx"></script>
~~~~

Then have the API URL module read and validate <code>window.__APP_CONFIG__.apiBaseUrl</code> before falling back to a safe local default. Ensure the deployed HTML uses the real hashed module asset generated by the build. The runtime file is public and should have a short cache lifetime or revalidate on each release.

Do not generate this file from server secret values. If the API URL is compiled into the JavaScript instead, build a separate artifact for each environment.

## 6. Configure the edge route order

Use the hosting platform's routing rules to implement this order:

| Request | Destination | Required behavior |
| --- | --- | --- |
| Existing hashed asset | Static asset directory | Return the asset with its content type |
| <code>/api</code> or <code>/api/*</code> | Express API service | Preserve the path expected by Express |
| Frontend route such as <code>/courses/mern</code> | React entry document | Allow direct navigation and refresh |
| Unknown API route | Express API service | Return an API not-found response, not frontend HTML |

The API route must take precedence over the SPA fallback. Verify both <code>/api</code> and nested <code>/api/*</code> behavior. Do not rewrite requests for missing API endpoints to <code>index.html</code>.

If deployed under a subpath such as <code>/learn/</code>, configure the Vite base path, React router basename, asset locations, and edge rewrites together.

## 7. Configure production response caching

| Resource | Suggested behavior |
| --- | --- |
| HTML entry document | Revalidate or use a short cache lifetime |
| Public runtime configuration | Revalidate or use a short cache lifetime |
| Content-hashed JS and CSS | Long cache lifetime with immutable behavior |
| Public images and fonts | Cache according to whether filenames are versioned |
| API responses | Use API-specific cache policy; do not cache private responses publicly |

A new HTML file can reference new hashed files while some users still have the previous document open. Keep old hashed assets available for the expected deployment overlap and browser cache lifetime.

## 8. Configure API settings for a same-origin deployment

| API setting | Example value | Reason |
| --- | --- | --- |
| Allowed browser origin | <code>https://learn.example.test</code> | Exact public application origin |
| API route prefix | <code>/api</code> | Same path the client and edge use |
| Session cookie | Secure, HttpOnly, host-only, suitable SameSite value | Restricts browser exposure |
| CSRF | Existing token flow enabled | Protects cookie-authenticated state changes |
| Trusted proxy hops | Actual edge-to-API path | Allows correct HTTPS awareness |
| MongoDB URI | Protected API runtime secret | Not sent to the browser |

A same-origin API path normally does not require CORS for browser requests. If the API also accepts cross-origin browser requests, maintain an explicit allowlist instead of wildcard credentialed access.

## 9. Alternative: separate frontend and API hosts

If the static frontend is at <code>https://learn.example.test</code> and the API is at <code>https://api.example.test</code>, the frontend's public base URL becomes:

~~~~text
VITE_API_BASE_URL=https://api.example.test/api
~~~~

Coordinate the related values:

| Component | Required setting |
| --- | --- |
| Frontend | Public API URL using HTTPS |
| API CORS | Exact origin <code>https://learn.example.test</code> and credentials enabled when sessions use cookies |
| Frontend fetch | <code>credentials: "include"</code> for cross-origin cookies |
| API session cookie | Secure and scoped to the API host unless a broader scope is necessary |
| CSRF | Existing CSRF token route and expected header available to the frontend |
| Edge | API hostname routes only to Express; frontend hostname routes only to static hosting |

Subdomain hosts are cross-origin, even when same-site. Verify browser behavior on the actual supported browsers. A frontend and API on entirely different sites may face third-party-cookie restrictions; avoid relying on a cookie setup that the target browsers block.

## 10. Build and publish the frontend

From the frontend package directory, create a repeatable release build:

~~~~text
npm ci
npm run build
~~~~

Before publishing:

1. Confirm the build used the intended public API base URL.
2. Inspect output assets and source maps for credentials and internal-only values.
3. Confirm the output's asset paths match the static host's base path.
4. Record the source revision and artifact identifier.
5. Publish assets without deleting the previous release's hashed files.
6. Revalidate the entry document and public runtime configuration.

## 11. Verify with browser requests

Use a browser session to verify the deployed site:

1. Open the application over HTTPS.
2. Open the Network panel and confirm API calls use the expected host and path.
3. Confirm the browser sends the session cookie only as intended.
4. Confirm state-changing requests include the existing CSRF token header.
5. Open a nested client route directly and refresh it.
6. Request a nonexistent API path and confirm the response is an API 404, not HTML.
7. Check the entry document, runtime config, and hashed asset cache headers.
8. Confirm errors do not expose cookies, authorization headers, or server secrets.

For a separate-origin setup, also inspect the preflight request and verify that the exact origin, method, allowed headers, and credentials match the API response.

## 12. Roll out a compatible client and server change

When changing an API shape:

1. Add the server behavior while keeping old clients compatible.
2. Deploy and verify the API.
3. Publish the new frontend artifact or runtime config.
4. Observe errors and client usage.
5. Remove old API behavior only after the agreed compatibility period.

Keep a previous compatible frontend artifact and its public configuration. If the new release fails, restore those together and route traffic back to the prior API version as needed.

## 13. Release review

- [ ] Frontend artifact comes from a reviewed source revision.
- [ ] The API URL is correct for this environment.
- [ ] No server secrets appear in the frontend bundle or runtime config.
- [ ] The edge forwards API routes before applying the SPA fallback.
- [ ] Static assets and nested client routes resolve after a hard refresh.
- [ ] API 404 responses are not replaced with frontend HTML.
- [ ] CORS, cookie, credential, and CSRF settings match the deployment origins.
- [ ] HTML and runtime config revalidate; hashed assets use versioned caching.
- [ ] Previous compatible assets are retained for rollback.
- [ ] Browser and server diagnostics contain no session cookies or credentials.
